# Funnel Runtime

Мини-платформа для многошаговых веб-воронок. Экраны описываются JSON-конфигом, конфиги версионируются, публикация и откат идут без передеплоя. Есть A/B-эксперимент с назначением варианта на сервере, собственный приём событий с дедупликацией и dashboard по уникальным сессиям.

- **Публичный URL:** https://web-production-eee72.up.railway.app — воронка, [/admin](https://web-production-eee72.up.railway.app/admin) (нужен `ADMIN_TOKEN`, передаётся отдельно), [/dashboard](https://web-production-eee72.up.railway.app/dashboard)
- **Репозиторий:** https://github.com/ssavl/test-saveliistepura
- Воронка открывается на `/` → `/f/workstyle-planner`. Параметры: `?utm_source=…&utm_medium=…&utm_campaign=…`, `?variant=A|B` (override), `?reset=1` (новая сессия).

Конфиги — те, что выданы с заданием: `configs/funnel-v1.json`, `configs/funnel-v2.json` и `configs/funnel-v3.json` (вторая итерация), воронка «workstyle-planner». Они лежат в репозитории без изменений, рантайм понимает их формат напрямую, без конвертации.

## Запуск локально

```bash
npm install
npm test                 # все тесты
npm run build            # web-экспорт в apps/web/dist
npm start                # сервер + web на http://localhost:3000 (при первом старте публикует configs/funnel-v1.json)
npm run traffic          # 160 синтетических сессий через HTTP API → откройте /dashboard
npm run traffic -- --publish configs/funnel-v2.json   # опубликовать v2 и дать трафик уже на неё
```

Режим разработки с hot reload: `npm run dev:server` и `EXPO_PUBLIC_API_URL=http://localhost:3000 npm run dev:web` (web на :8081).

Переменные окружения:
- `PORT` (по умолчанию 3000), `DB_PATH`, `CONFIGS_DIR`, `SEED_CONFIG`, `WEB_DIR`, `LOG=0`;
- `ADMIN_TOKEN` — если задан, `/api/admin/*` требует заголовок `x-admin-token`. На странице `/admin` токен вводится в поле.

Docker: `docker build -t funnel . && docker run -p 3000:3000 -v funnel-data:/data funnel`.

Деплой на Railway (сборка из Dockerfile, SQLite на volume `/data`):

```bash
railway init --name funnel-runtime
```

## Как это работает

### Конфиг и движок

Конфиг разбирается zod-схемой (`packages/shared/src/config.ts`). Неизвестные поля сохраняются (`looseObject`), поэтому новые метаданные в будущих версиях не ломают валидацию.

- **Шаги** лежат в `steps`, типы: `info`, `single-select`, `multi-select`, `number`, `result`. Тексты берутся из `content`, ограничения — из `input`, сообщения об ошибках — из `validation.messages` (их выводит UI). Ответ хранится под ключом `input.name`.
- **Порядок шагов** задаёт `experiment.variants.{A,B}.stepSequence`, у каждого варианта свой. Поэтому вариант может менять порядок и состав экранов: в v3 вариант B не показывает `tool_count`.
- **Ветвление** через `visibleWhen`: шаг показывается, только если условие выполняется на ответах, данных раньше в последовательности. Операторы: `eq`, `neq`, `in`, `nin`, `contains`, `gt`/`gte`/`lt`/`lte`, `exists`; составные `all`/`any`/`not`. Если ответа нет, условие ложно.
- **Устаревшие ответы.** Движок проходит последовательность и учитывает только ответы видимых шагов (`walk`). Пример: пользователь выбрал hybrid, ответил на `office_days`, вернулся и сменил режим на remote. Ответ про офисные дни больше не влияет ни на видимость, ни на результат.
- **Результат.** Срабатывает первое подходящее правило из `resultRules`, иначе берётся `defaultResultId`. Результат считает сервер по сохранённым ответам (`GET /api/sessions/:id/result`); клиент тем временем показывает `content.loadingTitle`, при ошибке — `errorTitle` и `retryLabel`. Переопределения варианта применяются глубоким слиянием: `stepOverrides` для текстов шагов, `resultOverrides` для формулировки результата и CTA.
- **CTA `expand_recommendation`** раскрывает список `recommendations` прямо на экране результата.
- **Прогресс** (`progress.countVisibleOnly`, `excludeTypes`) считает только видимые вопросы, без info и result. Если ответ открывает дополнительный шаг (`office_days`, `security_constraints`), знаменатель растёт.

При публикации конфиг проверяется (`validateConfig`) для обоих вариантов:
- все шаги последовательности существуют и не повторяются;
- в последовательности ровно один result-шаг, и он последний;
- `visibleWhen` ссылается только на ответы, которые даются раньше;
- все результаты из правил и `defaultResultId` существуют;
- ключи переопределений валидны, веса вариантов дают положительную сумму;
- после применения переопределений шаги остаются валидными.

Нарушение этих правил — ошибка, и публикация блокируется. Предупреждения (например, правило результата использует ответ, который этот вариант не спрашивает) публикацию не останавливают.

### Состояние сессии

`session_id` хранится в localStorage. Ответы и история шагов лежат на сервере (`sessions.state_json`), запись идёт с оптимистичной блокировкой по `rev`. Текущий шаг виден в URL (`/f/workstyle-planner/work_mode`). Поэтому:
- после refresh или повторного открытия пользователь возвращается на тот же шаг с теми же ответами;
- кнопка «Назад» в браузере обрабатывается как back внутри воронки: история обрезается и отправляется `back_clicked`;
- переход по URL на шаг вне истории перенаправляет на текущий шаг.

Срок жизни сессии — `session.ttlHours` (72 ч) с последней активности. После него открывается новая сессия на активной версии.

### Версии и откат

- `funnel_versions` — неизменяемые строки `(slug, version, config_json)`. Номер версии берётся из `config.version` в файле, поэтому `funnel_version` в событиях совпадает с файлом. Повторная публикация существующего номера возвращает 409: переключение на старую версию делается откатом или активацией.
- `funnel_active` — указатель на активную версию. Откат только переключает указатель, по умолчанию на ближайшую версию ниже активной. История действий пишется в `version_log`.
- Поле `status` файла (`draft`/`published`) показывается в админке как информация; активность определяет указатель.
- Сессия при создании запоминает `version`, `experiment_id` и `variant` (`pinVersion`, `pinExperimentVariant`). Сервер всегда отдаёт ей конфиг закреплённой версии, поэтому старые сессии доживают на своей версии после публикации и отката, а новые получают активную.

### A/B

Вариант назначается на сервере:

```
FNV1a(session_id + ":" + experiment.id) / 2^32 < weightB / (weightA + weightB)  →  B
```

Результат сохраняется в сессии. При refresh сессия продолжается, вариант не меняется. Для проверки можно передать `?variant=B`. Если override расходится с вариантом текущей сессии, создаётся новая сессия: назначение внутри одной сессии не меняется никогда.

**Эксперимент `question-order-and-result-framing`.** Вариант B:
1. начинает с контекстных вопросов (режим работы, часовые пояса) вместо числового ввода размера команды;
2. использует более «цепляющий» интро-экран;
3. формулирует результат как вывод о проблеме команды («Your hybrid model needs clearer rules») с конкретным CTA («See the 30-day action list»).

**Гипотеза.** Лёгкие вопросы о себе в начале снижают ранний отвал, а результат, сформулированный как проблема с понятным следующим шагом, повышает интерес к рекомендациям. Значит, в варианте B доля сессий, раскрывших action list, будет выше.

**Основная метрика:** `уникальные сессии с cta_clicked / уникальные начатые сессии` (CTA-конверсия от старта). На dashboard для неё есть 95% интервал Уилсона, абсолютный и относительный lift и p-value двустороннего z-теста для двух долей.

**Защитные метрики:** доля дошедших до результата, отвал на первом вопросе, распределение результатов: переформулировка не должна менять, какой результат получает пользователь.

`experiment.id` меняется между версиями (`…-v1`, `-v2`, `-v3`) и хранится в каждом событии. Сравнивать A и B корректно внутри одной версии: на dashboard есть фильтр по версии.

### События

`POST /api/events` принимает `{ events: [...] }`, не больше 500 событий за запрос. Конверт события совпадает с `events.baseProperties` из конфига, плюс два служебных поля:

| Поле | |
|---|---|
| `event_id` | uuid от клиента, первичный ключ: основа идемпотентности |
| `session_id` | uuid сессии |
| `name` | имя события |
| `client_timestamp` / `server_ts` | время клиента / время приёма, ставит сервер |
| `seq` | наше дополнение: монотонный счётчик событий сессии на клиенте (у `session_started` — 0), задаёт порядок независимо от прихода |
| `funnel_id`, `funnel_version`, `experiment_id`, `variant`, `utm_source`, `utm_medium`, `utm_campaign` | **сервер перезаписывает значениями из сессии**: клиенту здесь не доверяем |
| `step_id` | обязателен для шаговых событий и должен существовать в закреплённой версии и варианте |
| `properties` | свойства события, см. ниже |

**Состав событий задаёт конфиг закреплённой версии** (`events.allowed`):
- имя, которого нет в `allowed`, отклоняется. Например, `recommendation_expanded` принимается только от сессий на v3;
- свойства, не перечисленные для события, отбрасываются.

Свойства событий:
- `step_viewed {step_type, visible_step_index, visible_step_count}` — позиция среди видимых шагов всех типов;
- `answer_submitted {answer_kind}` — тип ответа. Сырые ответы в аналитику не попадают (`privacy.storeRawAnswers: false`), они живут только в состоянии сессии;
- `step_completed {next_step_id}`;
- `back_clicked {destination_step_id}`;
- `result_viewed {result_id}`;
- `cta_clicked {result_id, action}`;
- в v3: `recommendation_expanded {result_id, action, source}`.

Инварианты:
- `INSERT OR IGNORE` по `event_id`: дубль внутри пачки, между пачками или при повторе после timeout ничего не меняет;
- каждое событие валидируется отдельно. Ответ: `{accepted, duplicates, rejected[{index, reason}]}`, одно битое событие не мешает записи остальных;
- `session_started` пишет сервер при создании сессии, ровно один раз.

Клиент копит события в очереди в localStorage и отправляет их каждые 2 секунды, при накоплении 10 событий и на `pagehide` через `sendBeacon`. Из очереди удаляются только события, на которые пришёл ответ, поэтому повторная отправка безопасна.

### Правила агрегации

Все показатели — `COUNT(DISTINCT session_id)`:

| Показатель | Определение |
|---|---|
| Начали | сессии с любым событием, в том числе `session_started` |
| Увидел шаг X | сессии с `step_viewed`, `answer_submitted` или `step_completed` на X. Потерянное или опоздавшее событие не делает конверсию больше 100% |
| Завершил шаг X | сессии со `step_completed` на X (для результата — `cta_clicked`) |
| Конверсия шага | завершили / увидели; **reach** = увидели / начали |
| Отвал на X | сессия не дошла до результата, и X — последний увиденный шаг **по `seq`**, а не по порядку прихода событий |
| Дошли до результата | `result_viewed` или `cta_clicked` |
| CTR CTA | `cta_clicked` / дошедшие до результата |
| По результатам | сессии, увидевшие `result_id`, и их CTA |

Повторные просмотры и возвраты не удваивают счёт, потому что считаются уникальные сессии. Инвариант, закреплённый тестом: `Σ отвалов + отвал до первого шага + дошедшие до результата = начали`.

Порядок строк в таблице шагов — объединение `stepSequence` выбранных версий и вариантов: новые шаги встают рядом с предшественником, результат — последним. Срезы: variant, version, utm_campaign (включая `(none)`).

## Модель данных (SQLite)

```
funnel_versions(slug, version, config_json, note, created_at)       PK(slug, version), неизменяемая
funnel_active(slug PK, version, updated_at)                          указатель на активную версию
version_log(id, slug, action, from_version, to_version, at)          publish / rollback / activate
sessions(id PK, slug, version, experiment_id, variant, utm_json, state_json, rev,
         created_at, updated_at, expires_at)
events(event_id PK, session_id, slug, name, step_id, funnel_version, experiment_id, variant,
       utm_source, utm_medium, utm_campaign, utm_json, props_json, client_ts, seq, server_ts)
schema_migrations(version, applied_at)                               миграции применяются кодом при старте
```

Миграции лежат в `apps/server/src/db.ts` и только добавляются. Миграция 2 (поля `experiment_id`, `expires_at`, `utm_source`, `utm_medium`) — пример изменения схемы без ручных действий. Шаги, варианты, результаты и события живут в JSON-конфиге и в `events.name` (TEXT), поэтому новая версия конфига схему не меняет.

## Генератор трафика

```
npm run traffic -- [--sessions 160] [--seed 42] [--base-url URL] [--publish configs/funnel-v2.json] [--admin-token T]
```

Генератор ходит в реальный HTTP API как настоящий клиент и проходит воронку по движку из `shared`. Он генерирует:
- разные UTM-кампании;
- варианты A и B: в основном назначенные сервером, примерно 10% через override;
- все ветки и все результаты: remote/hybrid/office, meeting-heavy, compliance;
- отвал на разных шагах и возвраты назад со сменой ответа;
- дубли внутри пачки, повторную отправку пачек, пачки не по порядку, перемешанные события и битые события.

Флаг `--publish` перед генерацией публикует или активирует указанную версию. В конце генератор сравнивает ожидания с `/api/analytics`: сравнивается разница до и после запуска по уникальным сессиям, вариантам, кампаниям, версиям, шагам и результатам.

## Вторая итерация (funnel-v3.json)

Изменения в v3 по сравнению с v2:
- новая условная ветка: при выборе `compliance` в `priorities` показывается `security_constraints`, появляется результат `regulated_scale`;
- в варианте B удалён экран `tool_count`;
- новое событие `recommendation_expanded`: клиент шлёт его, только если закреплённая версия его разрешает.

Порядок проверки:
1. Открыть `/admin`, выбрать `funnel-v3.json`, нажать «Проверить», затем «Опубликовать».
2. Старая вкладка на v2 (в том числе B-сессия на шаге `tool_count`) продолжает работать.
3. Новая сессия получает v3.
4. «Откатить на предыдущую»: новые сессии снова получают v2, сессии на v3 доживают на v3.

Схема БД при этом не меняется, аналитика по всем версиям сохраняется (срез по версиям). Сценарий закреплён тестом `apps/server/test/iteration2.test.ts`.

## Тесты

- `packages/shared/test/engine.test.ts` — на выданных конфигах: валидность v1–v3, порядок и тексты B, `visibleWhen`, отбрасывание устаревших ответов, прогресс, сообщения валидации из конфига, правила результата (`any`/`all`, meeting-heavy, compliance), отказ на битых конфигах.
- `apps/server/test`:
  - `versions`: публикация с номером из файла, 409 на повтор, откат, закрепление версии, конфликт `rev`;
  - `sessions`: стабильность и веса A/B, override, единственный `session_started`, TTL, результат на сервере;
  - `events`: дедупликация, повтор пачки, изоляция битых событий, allowlist событий и свойств по версии;
  - `analytics`: сценарий с дублями, back, событиями не по порядку, срезами и результатами;
  - `iteration2`: v1 → v2 → v3 → откат.

## Допущения и ограничения

- `visible_step_index`/`visible_step_count` в `step_viewed` — позиция среди всех видимых шагов, включая info и result. Прогресс-бар следует `progress.excludeTypes` и считает только вопросы.
- `answer_kind` = тип шага (`number`, `single-select`, …).
- `?variant=` читается до загрузки конфига, поэтому имя параметра фиксировано. Оно совпадает с `overrideQueryParam` во всех выданных конфигах.
- `status: draft` в файлах v2/v3 трактуется как информационное поле: публикует администратор.
- «Отвал» включает сессии, которые ещё в процессе: отдельного тайм-аута для аналитики нет.
- Админка защищена только `ADMIN_TOKEN`, без пользователей и ролей.
- Аналитика считается SQL-запросами на лету, без предагрегации. Для тестового объёма этого достаточно.
- SQLite требует постоянного диска на хостинге.
