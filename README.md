# Funnel Runtime

Мини-платформа для многошаговых веб-воронок: экраны описываются JSON-конфигом, конфиги версионируются с публикацией и откатом без передеплоя. Есть A/B-эксперимент с назначением варианта на сервере, собственный приём событий с дедупликацией и dashboard по уникальным сессиям.

- **Публичный URL:** _TBD_
- Воронка: `/` → `/f/bible-plan` (параметры: `?utm_campaign=…&utm_source=…`, `?variant=A|B`, `?reset=1`)
- Управление версиями: `/admin` · Аналитика: `/dashboard`

Контент вымышленный: онбординг приложения «Orthodox Bible», который собирает личный план чтения Писания.


## Запуск локально

```bash
npm install
npm test                 # все тесты
npm run build            # web-экспорт в apps/web/dist
npm start                # сервер + web на http://localhost:3000 (при первом старте публикует configs/v1.json)
npm run traffic          # 160 синтетических сессий через HTTP API → откройте /dashboard
```

Режим разработки с hot reload: `npm run dev:server` и `EXPO_PUBLIC_API_URL=http://localhost:3000 npm run dev:web` (web на :8081).

Переменные окружения: `PORT` (3000), `DB_PATH`, `CONFIGS_DIR`, `SEED_CONFIG`, `WEB_DIR`, `ADMIN_TOKEN` (если задан, `/api/admin/*` требует заголовок `x-admin-token`, токен вводится на странице `/admin`), `LOG=0`.

Docker: `docker build -t funnel . && docker run -p 3000:3000 -v funnel-data:/data funnel`.

## Как это работает

### Конфиг воронки

Типы экранов: `single`, `multi` (min/max), `number` (min/max, бакеты для аналитики), `info`, `result` (CTA и шаблоны `{{label:stepId}}` / `{{value:stepId}}`). Переходы задаются списком `next: [{ when?, to }]`: срабатывает первый подходящий переход, переход без `when` — по умолчанию. Условия: `in` (для single/multi), `gte` и `lt` (для number).

Варианты эксперимента описываются в `variants.A|B`:
- `steps.<id>` — поверхностный патч полей шага (тексты, опции, `next` для перестановки шагов, контент результата);
- `start` — другой стартовый шаг;
- `removeSteps` — удалить шаги. Переходы, которые вели в удалённый шаг, автоматически перенаправляются на его следующий шаг по умолчанию.

При публикации конфиг проверяется для обоих вариантов (`validateConfig`): все цели переходов существуют, у каждого не-результата есть переход по умолчанию, нет циклов, результат достижим, есть хотя бы одно условное ветвление. Недостижимые шаги дают предупреждение, остальные нарушения — ошибку, и публикация блокируется.

**Прогресс** равен `|история| / (|история| + остаток предсказанного пути)`. Остаток пути вычисляется по текущим ответам; условия по ещё не заданным ответам уходят в ветку по умолчанию. Поэтому считаются только шаги, доступные этому пользователю: например, ответ «5 минут» добавляет экран-подсказку, и знаменатель растёт на один.

**Состояние.** `session_id` хранится в localStorage, ответы и история шагов — на сервере (`sessions.state_json`, запись с оптимистичной блокировкой через `rev`). Текущий шаг есть в URL (`/f/bible-plan/minutes`). Из этого следует:
- после refresh или повторного открытия страницы пользователь возвращается на тот же шаг с теми же ответами;
- кнопка «Назад» в браузере обрабатывается как back внутри воронки: история обрезается и отправляется `back_clicked`;
- переход по URL на шаг, которого нет в истории, перенаправляет на текущий шаг.

### Версии и откат

`funnel_versions` — неизменяемые строки `(slug, version, config_json)`. `funnel_active` — указатель на активную версию. Публикация добавляет версию N+1 и переключает указатель; откат только переключает указатель, по умолчанию на ближайшую версию ниже активной. Все действия пишутся в `version_log`.

Сессия при создании запоминает `version` и `variant`, и сервер **всегда** отдаёт ей конфиг закреплённой версии. Отсюда:
- старые сессии продолжают работать после публикации или отката;
- новые сессии получают активную версию;
- аналитика хранит версию в каждом событии, поэтому данные не теряются.

### A/B

Вариант назначается на сервере: `FNV1a(session_id + ":" + experiment.key) / 2^32 < splitB → B`, результат сохраняется в `sessions.variant`. При refresh сессия продолжается, вариант не меняется. Для проверки можно передать `?variant=B`. Если он расходится с вариантом текущей сессии, создаётся новая сессия: назначение внутри сессии не меняется никогда.

**Гипотеза.** Если спрашивать о ежедневном времени сразу после цели (вариант B меняет порядок: цель → минуты → опыт), а результат показывать как конкретное первое чтение на сегодня («Мк 1:1–20, 15 минут») с социальным доказательством, то больше пользователей нажмут CTA. Причина: обязательство, данное раньше, и ощутимый первый шаг снижают трение.

**Основная метрика:** `уникальные сессии с cta_clicked / уникальные начатые сессии` (CTA-конверсия от старта). На dashboard для неё показаны 95% интервал Уилсона, абсолютный и относительный lift и p-value двустороннего z-теста для двух долей. Защитные метрики: доля дошедших до результата и отвал на первом экране.

### События

`POST /api/events` принимает `{ events: [...] }`, не больше 500 событий за запрос.

| Поле | |
|---|---|
| `event_id` | uuid от клиента, первичный ключ: основа идемпотентности |
| `session_id` | uuid сессии |
| `name` | `session_started`, `step_viewed`, `answer_submitted`, `step_completed`, `back_clicked`, `result_viewed`, `cta_clicked`, а также события из конфига (`^[a-z][a-z0-9_]{2,47}$`) |
| `client_ts` / `server_ts` | время клиента / время приёма, ставит сервер |
| `seq` | монотонный счётчик событий внутри сессии на клиенте (у `session_started` — 0) |
| `funnel_version`, `variant`, `utm` | **сервер перезаписывает значениями из сессии**: клиенту здесь не доверяем |
| `step_id` | обязателен для шаговых событий |
| `props` | свойства конкретного события: `{index,total}` у `step_viewed`, `{option}/{options}/{bucket}` у `answer_submitted`, `{to, via}` у `back_clicked`, `{url}` у `cta_clicked` |

Инварианты:
- `INSERT OR IGNORE` по `event_id`: дубль внутри пачки, между пачками или при повторе после timeout ничего не меняет.
- Каждое событие валидируется отдельно. Ответ: `{accepted, duplicates, rejected[{index, reason}]}`. Одно битое событие не мешает записи остальных.
- `session_started` пишет сервер при создании сессии, ровно один раз.
- Приватность: число из ответа не покидает состояние сессии, в событие попадает только бакет (`10-20`). У `answer_submitted` сервер отбрасывает все props, кроме `option`, `options` и `bucket`.
- Клиент копит события в очереди в localStorage и отправляет их каждые 2 секунды, при накоплении 10 событий и на `pagehide` через `sendBeacon`. Из очереди удаляются только события, на которые пришёл ответ, поэтому повторная отправка безопасна.

### Правила агрегации

Все показатели — `COUNT(DISTINCT session_id)`:

| Показатель | Определение |
|---|---|
| Начали | сессии с любым событием, в том числе `session_started` |
| Увидел шаг X | сессии с `step_viewed`, `answer_submitted` или `step_completed` на X. Потерянное или опоздавшее событие не делает конверсию больше 100% |
| Завершил шаг X | сессии со `step_completed` на X (для результата — `cta_clicked`) |
| Конверсия шага | завершили / увидели; **reach** = увидели / начали |
| Отвал на X | сессия не дошла до результата, и X — последний увиденный шаг **по `seq`**, а не по порядку прихода событий |
| Дошли до результата | `result_viewed` или `cta_clicked` |
| CTR CTA | `cta_clicked` / дошедшие до результата |

Повторные просмотры и возвраты не удваивают счёт, потому что считаются уникальные сессии. Инвариант, закреплённый тестом: `Σ отвалов + отвал до первого шага + дошедшие до результата = начали`.

Порядок строк в таблице шагов — объединение BFS-путей конфигов выбранных версий и вариантов: ветки стоят рядом с родительским шагом, результат — последним. Шаги, которые встречаются только в событиях, добавляются в конец. Доступные срезы: variant, version, utm_campaign (включая `(none)`).

## Модель данных (SQLite)

```
funnel_versions(slug, version, config_json, note, created_at)        PK(slug, version), неизменяемая
funnel_active(slug PK, version, updated_at)                           указатель на активную версию
version_log(id, slug, action, from_version, to_version, at)           publish / rollback / activate
sessions(id PK, slug, version, variant, utm_json, state_json, rev, created_at, updated_at)
events(event_id PK, session_id, slug, name, step_id, funnel_version, variant, utm_campaign,
       utm_json, props_json, client_ts, seq, server_ts)               индексы (session_id, seq), (slug, name, step_id)
schema_migrations(version, applied_at)                                миграции применяются кодом при старте
```

Новые шаги, варианты и события живут в JSON-конфиге и в `events.name` (TEXT). Поэтому вторая итерация не требует изменения схемы.

## Генератор трафика

`npm run traffic -- --sessions 160 --seed 42 [--base-url http://localhost:3000]` ходит в реальный API как настоящий клиент. Он генерирует:
- разные UTM-кампании;
- варианты A и B: в основном назначенные сервером, примерно 10% через override;
- прохождение разных веток;
- отвал на разных шагах и возвраты назад;
- дубли внутри пачки, повторную отправку пачек, пачки не по порядку и перемешанные события;
- битые события.

В конце генератор сравнивает свои ожидания с `/api/analytics`: сравнивается разница до и после запуска, по уникальным сессиям.

## Вторая итерация

`configs/v2.json` — репетиция изменений из ТЗ:
- новая условная ветка: при `goal=fast` показывается экран `fast_choice`;
- для варианта B удалён экран `welcome` (`removeSteps`);
- новое событие `plan_preview_opened` через `secondaryAction` на экране результата. Событие задаётся в конфиге, поэтому фронтенд не нужно передеплоивать.

Порядок проверки:
1. Открыть `/admin`, выбрать `v2.json`, нажать «Проверить», затем «Опубликовать».
2. Старая вкладка на v1 (в том числе вариант B, стоящий на `welcome`) продолжает работать.
3. Новая сессия получает v2.
4. «Откатить на предыдущую»: новые сессии снова получают v1, сессии на v2 доживают на v2, а аналитика по обеим версиям сохраняется (срез по версиям).

Весь сценарий закреплён тестом `apps/server/test/iteration2.test.ts`.

## Допущения и ограничения

- Исходные два конфига из ТЗ не были предоставлены: контент и формат конфига — наши.
- «Отвал» включает сессии, которые ещё в процессе. Тайм-аут неактивности не вводился, для демо-объёмов это нормально.
- Админка защищена только опциональным `ADMIN_TOKEN`, без пользователей и ролей.
- Аналитика считается SQL-запросами на лету, без предагрегации. Для тестового объёма этого достаточно, для миллионов событий понадобились бы материализованные агрегаты.
- `client_ts` может врать, поэтому порядок определяется `seq` клиента. Если клиент сбросит localStorage, начнётся новая сессия.
- Одна активная версия на воронку, один эксперимент на версию, сплит A/B задаётся в конфиге.
- SQLite требует постоянного диска на хостинге.
